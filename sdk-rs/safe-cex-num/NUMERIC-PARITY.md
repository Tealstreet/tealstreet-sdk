# Numeric parity investigation: production-reachable disagreement

Round 4 paused implementation on accepted-input reachability; round 5 resumed
with the submitted-order bar below. No portable fdlibm specialisation is retained.
The split gate now pins complete corpus contents. These measurements describe
the measured configurations, with the limits recorded below.
For the arithmetic contract, see [safe-cex guidance](../../packages/safe-cex/CLAUDE.md)
and `safe-math.ts`.

## Reachable TWAP sizing input

`TwapHandler.handle` accepts `twap:start` options without a lower bound on
`randomnessPercentage`. `TwapInstance.createNewState` computes
`multiply(random(0, randomnessPercentage), 0.01)`. With the accepted option
`randomnessPercentage = 1e-24`, a valid random draw of `0.5` makes the actual
lodash `random` return exactly `1e-24`. The live TypeScript then disagrees:

| Configuration | Result | Binary64 bits |
| --- | --- | --- |
| Node 24.20.0, macOS ARM64, standard Math.pow | 9.999999999999999e-27 | 3a88c240c4aecb13 |
| Same runtime, `--no-use-std-math-pow` | 1.0000000000000002e-26 | 3a88c240c4aecb15 |

These values differ by two ULPs. This proves reachability through accepted
production options, rather than evidence of actual user settings or a changed
submitted exchange lot. Ordinary market metadata and order size suffice; the
small value here is the TWAP randomness option. Ordinary caller settings are 5
or 10, and this tiny multiplier discrepancy does not survive submitted-size
rounding under the round-5 bar. No TypeScript fix was attempted.

Reproduce from the repository root with the following script, under each mode:

```js
const fs = require('node:fs');
const { stripTypeScriptTypes } = require('node:module');
const oldRandom = Math.random;
Math.random = () => 0.5;
const random = require(process.cwd() + '/node_modules/lodash/random');
Math.random = oldRandom;
const source = fs.readFileSync('packages/safe-cex/src/utils/safe-math.ts', 'utf8')
  .replace(/^import .*;$/mg, '').replace(/export /g, '');
const math = new Function(stripTypeScriptTypes(source) + '; return { multiply };')();
const input = random(0, 1e-24);
const result = math.multiply(input, 0.01);
const bits = Buffer.alloc(8);
bits.writeDoubleBE(result);
console.log({ input, result, bits: bits.toString('hex') });
```

## Why the local run was green

The local include-ignored run executed the real TypeScript differential;
it did not skip the test. Repeated full oracle generations were identical
within each measured configuration. Local ARM Rust arithmetic matched the
local standard-mode expectations. Linux x64 CI used a different runtime/platform
combination and failed `add(0, 1e-23)`. A pinned case count could not expose
changed expected contents across those configurations.

Measured complete JSON SHA-256 values:

- Standard ARM mode: `70057ffd597fedf2eff98221789ac6bcd21d861e9658a0227aebf6c737d83119`
- Legacy ARM mode: `49b80ed1ed553801cc190ee95fa519e8a0d29befa1f1c6afa3d2d0f1446ab082`

Legacy Node 22.23.2 ARM produced the same second hash. These historical investigation hashes also appear in the committed configuration
pins. Legacy V8 also permits architecture
and FP-contraction differences; a C++ no-contraction reconstruction is not an
observed engine configuration and must not populate an engine-value allowlist.

## Known runtime limitation

Bun and Safari use JavaScriptCore rather than V8. JavaScriptCore Math.pow has
not been measured here. Pinning an oracle makes a gate deterministic, but does
not make the shipped TypeScript deterministic across product runtimes.
The 13,367 count covers only the two measured ARM V8 modes; it does not claim
coverage of Linux x64 or JavaScriptCore disagreements.

## Submitted-order triage bar

Assess divergences by whether they change a submitted price or quantity **after
venue tick-size or lot-size rounding**, rather than whether a signature accepts
the input. Report a demonstrated submitted-order difference immediately.
Acceptance or a synthetic rounding example alone does not establish that finding.

For this audit, the overseer supplied the operational assumption that supported
venue increments are around `1e-8` or larger and the placement path does not
amplify these tiny discrepancies. Resolve cases whose results are all below
`1e-12` wholesale: these magnitudes are four orders below venue increments.
Revisit that classification if supported increments or downstream arithmetic
change. Only larger result bands require bounded caller and rounding assessment.

Nine synthetic half-tick candidates deserve explicit names: add/subtract with

no normal caller producing them or different submitted order was established.
Other add/subtract rows also contain extremely small operands rather than
ordinary venue price/quantity increments. Large outputs alone do not make those
input tuples a plausible placement path.

The two ordinary-input multiply cases (indices 241858 and 245631) are symmetric
`multiply(1.0000000000000002, 1e-7)`. Linux standard mode returns

Actual `adjust` yields identical values across tested power-of-ten steps from `1e-8` through

Default-precision divide discrepancies use extremely small denominators; audited
callers divide by price, contract size, maximum size, or an integer split count.
Examples retaining differences after synthetic rounding include
`divide(1e-8, 1e-23)` (index 364338), `divide(1e-11, 1e-23)` (365370),
`divide(1e-178, 1e-218)` (423013), and `divide(1e-203, 1e-218)` (431613).
None has a demonstrated ordinary venue placement path. The unusual precision

which omit precision.

This bounded audit established no actual submitted-order divergence. It does not
prove a universal absence for every future caller, market, or rounding step.

## Committed split gate and regeneration

The complete 476,804-row baseline is regenerated in memory from a pinned live
oracle. On disagreement rows, the recorded baseline configuration's observation
restores its encoding anchor; on agreement rows, the live result is already the
common answer. The regenerated baseline must match its committed SHA-256.
`tests/corpus/engines-disagree.json` lists all 13,933 exceptional rows, their full
input tuples, and the observed result for each measured configuration, including
the TWAP tuples. The remaining 462,871 rows require bit-exact Rust equality.
Exceptional rows accept an observed value or a one-ULP neighbor of an observed
finite nonzero value. NaN, infinities, and signed zero require exact classification.
Agreement rows receive no allowance.

`tests/corpus/pins.json` pins SHA-256 over the regenerated full baseline, disagreement file,
input tuples, and each complete measured output corpus. The gate reconstructs
and checks every recorded configuration, then runs both live modes and validates
their complete hashes. A count-preserving generator change, missing disagreement,
unknown configuration, or changed expected value fails; CI never expands the set.
Node 24.20.0 is required for this explicit live gate. Default `cargo test` remains
hermetic. From `sdk-rs`, run:

```sh
node --test safe-cex-num/tests/gate.test.cjs
cargo test --locked -p safe-cex-num --all-targets -- --include-ignored --nocapture
```

From the repository root, capture actual outputs using
`node sdk-rs/safe-cex-num/tests/measure.cjs <fresh-directory>` on each platform,
then regenerate using `node sdk-rs/safe-cex-num/tests/build-corpus.cjs <directories...>`.
Only pass actual observations, retain every measured configuration, and review
changes to both hashes and explicit disagreement rows. The Linux Actions job
captures and validates both real modes on every relevant change. JavaScriptCore
remains unmeasured; this split describes measured configurations, rather than
an assertion that all engines everywhere agree.

## Why the baseline is regenerated and disagreements are committed

Root [CLAUDE.md](../../CLAUDE.md), under its commit guidance, says **"NEVER commit
generated artifacts"** and explicitly names corpus dumps: repeated reports grew
to 712MB before a history purge. The reproducible full baseline therefore stays
out of Git; its hash provides the same content guarantee, checked after in-memory
regeneration. The minified `engines-disagree.json` remains committed because its
observations are irreplaceable input from configurations that cannot all be
reproduced locally or in one CI job. It is the evidence needed to reconstruct and
validate those other configurations, rather than a disposable generated report.
